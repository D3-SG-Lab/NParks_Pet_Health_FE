# AQC Animal Health: mock API responses for the backend

The mobile app runs on an in-memory mock today. This folder holds the JSON **those mock APIs return to the screens**. Use it as the reference for response shapes: if the real API returns the same JSON, the app's screens work unchanged.

- Every file was generated by calling the app's real data functions (`src/features/*/*Api.ts`). Nothing was typed by hand, so the JSON is exactly what the current UI renders.
- The clock was frozen at **Mon 26 Oct 2026 10:30, Asia/Singapore** (AM session, after the 08:00 due time). This gives due, overdue and done items all at once.
- `types.ts` is a copy of the app's domain types (`src/domain/types.ts`), the field-level contract. Wrapper shapes such as `AnimalListItem` and `CaseDetail` are described below and defined in the matching `*Api.ts`.
- To regenerate after the UI changes, run `npm run mock:export` (script: `scripts/export-mock-api.ts`). It rewrites everything here except this README.

## File format

Each JSON file is one example:

```json
{
  "endpoint": "GET /cases/{caseId}",
  "description": "What the screen uses it for",
  "role": "officer",
  "request": { "caseId": "C-2026-0142" },
  "response": { "...": "exactly what the app expects back" }
}
```

- `response` is the part the backend should match.
- `request` shows path, query or body values.
- `role` is the signed-in user. `*.officer.json` and `*.contractor.json` pairs show the same endpoint for each role.
- **The endpoint paths are proposals.** The app has no URLs yet, so name them however you like. The response shapes are what matter.

## Conventions

| Thing | Format | Example |
|---|---|---|
| Timestamps (`at`, `submittedAt`, `recordedAt`, `updatedAt`, …) | epoch **milliseconds**, number | `1792981800000` |
| Calendar dates (`date`, `arrivalDate`, `dueDate`, `startDate`, …) | ISO `YYYY-MM-DD`, Singapore local date | `"2026-10-26"` |
| Times of day (`time`, schedule `times`) | `HH:MM`, 24 h, Singapore local | `"08:00"` |
| Dose slot | `YYYY-MM-DDTHH:MM`, local, no zone | `"2026-10-26T07:30"` |
| AI confidence | number from 0 to 1 | `0.92` |
| IDs | opaque strings | `"animal-2"`, `"C-2026-0142"` |
| Missing values | `null`, never omitted. The exceptions are fields marked optional (`?`) in `types.ts`, such as `CaseEvent.detail` and `MediaItem.durationSec` | |

## Rules the API must enforce

The app hides things in the UI, but the backend has to enforce these:

1. **Who and when come from the server.** Request bodies never contain the user or the time. Fields such as `recordedBy`, `by`, `submittedBy`, `confirmedBy` and every timestamp are filled in by the server from the access token and the server clock.
2. **Contractor kennel scoping (BE-005).** Contractors only see animals in their assigned kennels (seed: `KC2-1`…`KC2-6`). That applies to lists, the inspection board, medication, cases and profiles. Opening an animal outside their kennels returns an error (see `animals/profile.error-out-of-scope.json`; suggested status 403).
3. **Officer-only actions.** Contractors can't do these:
   - create arrivals
   - use the review queue
   - confirm AI routing from the queue
   - close cases

   The contractor role is checked in `cases/close.error-forbidden.json`. `observationsNeedingReview` in the operations summary is only shown to officers, so you may return `0` for contractors.
4. **One record per slot.** There is one AM and one PM inspection per animal per day, and one administration per dose slot. A second attempt is a conflict (suggested 409).
5. **Microchip numbers are unique across active stays.**

## Errors

The mock throws typed errors, and the app shows their `message`. Each example file shows `{ error, kind, message }`. In the real API, a body like the one below works with the app, as long as `code` uses the same `kind` values:

```json
{ "code": "already_recorded", "message": "The AM inspection for Mochi was already recorded." }
```

| Area | `kind` values |
|---|---|
| Arrivals | `microchip_taken`, `incomplete` |
| Inspections | `already_recorded`, `not_found` |
| Medication | `already_recorded`, `not_due`, `not_found` |
| Observations | `empty`, `not_found`, `no_animal`, `already_routed`, `invalid_case` |
| Cases | `not_found`, `forbidden`, `invalid_transition`, `reason_required`, `empty` |
| Any animal-scoped call | out of scope → 403 |

## Endpoints

### Reference data
| Proposed endpoint | Example | Used by |
|---|---|---|
| `GET /kennels` | `reference/kennels.json` | New Arrival kennel picker (`occupant` = animal currently in it, or null) |
| `GET /vets` | `reference/vets.json` | Arrival Exam vet picker |
| `GET /countries` | `reference/countries.json` | New Arrival country picker |
| `GET /clinical-signs` | `reference/clinical-signs.json` | AQC symptom taxonomy (AI extraction, sign editor) |
| `GET /staff/assignable` | `reference/assignable-staff.json` | Case assignee picker (officer-side staff, no contractors) |

### Operations (home tab)
| Proposed endpoint | Example | Notes |
|---|---|---|
| `GET /operations/summary` | `operations/summary.{officer,contractor}.json` | Counts and alerts for the current session. Each alert includes `animalName` and `kennel`. An `overdue` alert is raised 2 h after the session due time (AM 08:00, PM 16:00). |

### Animals
| Proposed endpoint | Example | Notes |
|---|---|---|
| `GET /animals` | `animals/list.{officer,contractor}.json` | Active animals in kennel order. Each item is `{ animal, session, sessionDone, unwell, status }`. `unwell` = the animal has an open case. `status` is `unwell`, `due` or `active`. The app does search and filtering itself. |
| `GET /me/recent-animals` | `animals/recent.json` | Animal IDs, newest first, max 3. `POST` adds one when the user picks an animal. |
| `GET /animals/{id}/profile` | `animals/profile.json` | `{ animal, timeline, summary, cases, openCases, medicationCount, stayDay, stayLength, today }`. `timeline` is newest first, covering 30 days. `summary.statements[].refs` are 1-based indexes into `summary.sources` (AI-005). |
| `GET /records/{kind}/{id}` | `animals/record-detail.{inspection,observation,medication,exam,case}.json` | Detail sheet when a timeline row or summary citation is tapped. |

### Daily inspection
| Proposed endpoint | Example | Notes |
|---|---|---|
| `GET /inspections/board?session=&date=` | `inspections/board.{AM,PM}.{officer,contractor}.json` | `{ date, session, items[], doneCount }`. Each item is `{ animal, record \| null, lastCheckAt, openCaseId }`. |
| `POST /inspections` | `inspections/submit.normal.json`, `submit.abnormal.json`, `submit.error-already-recorded.json` | Returns `{ record, linkedCaseId, sentForReview }`. Abnormal findings either link to an open case for the same body system or go to the review queue. |

### Medication
| Proposed endpoint | Example | Notes |
|---|---|---|
| `GET /medication/animals?date=` | `medication/animals.{officer,contractor}.json` | Animals with medication today: `{ animal, scheduleCount, dueCount, overdueCount }`, those needing a dose first. |
| `GET /animals/{id}/medication?date=` | `medication/day.json` | Today's dose slots. A dose is `due` from 1 h before its time to 1 h after, then `overdue`. Before that it's `upcoming`; once recorded it's `administered`, with the record in `administration`. |
| `POST /medication/administrations` | `medication/record.json`, `record.error-already-recorded.json` | Body is `{ scheduleId, slot, remarks }`. Returns the administration. A dose that is still `upcoming` is rejected with `not_due`. |

### Observations and AI
| Proposed endpoint | Example | Notes |
|---|---|---|
| `POST /observations` | `observations/submit.json` | Saved immediately with `status: "processing"` and `ai: null`. The app polls the detail until the AI result arrives. |
| `GET /observations/{id}` | `observations/detail.{after-ai,awaiting-confirmation,review,routed}.json` | `{ observation, animal, cases }`. `status` goes `processing` → `awaiting-confirmation` (confident match) or `review` (no match, low confidence or AI unavailable) → `routed`. |
| `POST /observations/{id}/routing` | `observations/confirm-routing.json` | Confirm & Route. The body is `{ animalId, signs, action, caseId }`, where `action` is one of `timeline-only`, `update-case`, `new-case` or `reopen-case`. Returns `{ caseId, animalId }`. |
| `POST /observations/{id}/send-to-review` | (no body, no response) | The "Correct" button: moves the observation to the review queue. |
| `GET /observations/review-queue` | `observations/review-queue.json` | Officers only. Each item is `{ observation, reason, guess, guessCase, candidates }`. Order: `no-match`, then `low-confidence`, then `ai-unavailable`, newest first within each. |

### Cases
| Proposed endpoint | Example | Notes |
|---|---|---|
| `GET /cases` | `cases/list.{officer,contractor}.json` | `{ healthCase, animal, assignee, overdueFollowUps }`. Open work comes first, then most recently updated. The app does filtering and search itself. |
| `GET /cases/{id}` | `cases/detail.{open,review,closed}.json` | `{ healthCase, animal, assignee, summary, pendingObservationId }`. `healthCase.events` is the full history, oldest first, kept across reopen. |
| `POST /cases/{id}/close` | `cases/close.json`, `close.error-*.json` | Body is `{ reason, note }`. Officers only, and a reason is required. Valid reasons: `Resolved`, `Resolved after treatment`, `No longer a concern`, `Animal released`, `Duplicate case`. |
| `POST /cases/{id}/assign` | n/a | `{ staffId }` |
| `POST /cases/{id}/follow-ups` | n/a | `{ text, dueDate }` |
| `PATCH /cases/{id}/follow-ups/{followUpId}` | n/a | `{ done }` |
| `POST /cases/{id}/notes` | n/a | `{ text }` |
| `POST /cases/{id}/reviewed` | n/a | Marks a `review` case as reviewed (status → `open`). |
| `POST /cases/{id}/reopen` | n/a | Manual reopen of a closed case. Invalid status changes → `invalid_transition` (409). |

The app doesn't use the response body of the case actions without examples: after each one it reloads the case, so returning the updated `GET /cases/{id}` body or `204` both work. Each action adds a `CaseEvent` to `healthCase.events`.

### Arrivals
| Proposed endpoint | Example | Notes |
|---|---|---|
| `GET` / `PUT` / `DELETE /arrivals/draft` | `arrivals/draft.json` | Autosaved New Arrival draft, one per user. Dates are kept as typed (`DD/MM/YYYY`). |
| `GET /animals/microchip/{microchip}/taken` | `arrivals/microchip-check.json` | `{ taken }`. |
| `POST /arrivals` | `arrivals/complete.json`, `complete.error-microchip-taken.json` | Creates the animal stay and its baseline exam in one call, and returns the new `Animal`. Officers only. `weightKg` arrives as the typed string; validate it on the server. |

### Not backend endpoints (shapes documented for completeness)
| Example | Notes |
|---|---|
| `sync/state.json` | The device's offline outbox (Pending sync screen). On the server side, offline records simply arrive later through the normal POST endpoints, in order, and should be idempotent. |
| `notifications/push.json` | Push payload (`{ id, title, body, at, target }`, where `target` opens a case or an animal). It must not carry sensitive health data. |
